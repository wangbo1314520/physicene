# 通用要求 · 防假修 22 条（2026-10-10 第 21/22 条新增）

> 第 1-20 条沿袭各轮交付的标准约束（独立 commit / 物理断言 / 真实 UI / 参数链 / 两套渲染器等）。
> 第 21/22 条由星体时间线矛盾教训引入。

## 一、防假修（1-4）
1. 每项独立 commit + 独立报告
2. 不许改测试让过——红了查代码，不许改断言
3. 每项至少 1 条物理断言（不是"能跑"）
4. E2E 必须走真实 UI 入口，非旁路

## 二、防"改一半"（5-8）
5. 两套渲染器同步（BuilderCanvas + threeScene）
6. 参数链过 v2/v3/v4（catalog / RunBridge / Java 三层）
7. 默认值三处一致（catalog / RunBridge fallback / Java）
8. 检查器升级：case 是 fallback Box 不算"已覆盖"

## 三、防漏（9-11）
9. 改动前先答"影响哪些文件/哪些卡/哪些测试"
10. 改完自查要报"假阴性"（如说缺失 0 但实际全是方块）
11. 全量回归——不许只跑 verify（verify 只含 ts+vitest，不含 E2E）

## 四、报告格式（12-13）
12. 状态：✅/⚠️/🛑
13. commit hash

## 五、红线（14-16）
14. 遇到决策点停 + 报告 + 跳下一个——不许猜用户意图
15. 不许 force push
16. 每步跑 verify + 相关 E2E，红就停

## 六、自我检查（17-20）
17. 我改的文件，两套渲染器都改了吗？
18. 我加的元件，物理单测 + 渲染 + E2E 都有吗？
19. 我报的"完成"，有 diff / 截图 / 数据证据吗？
20. 我跑的全量回归，包含 E2E 吗？

## 七、流程纪律（21-22 新增 2026-10-10）

### 第 21 条：指令交叉时——停下、报告、问用户
当收到两条可能矛盾的指令时（如先到的"开工"与后到的"等批准"），
**不许假设先到的覆盖后到的**。必须：
- 停下当前工作
- 报告已收到两条指令及其矛盾点
- 问用户以哪条为准
- 等用户明确回复后再继续

违反后果：视为擅自行动，交付物不被验收（星体 A 档案例）。

### 第 22 条：长任务中间报告
预估 >0.5d 的任务（引擎/元件/渲染/卡/接线等各阶段），
每个阶段完成后**立即报一次**（≤10 行），不许一口气做完全程再报。
目的：用户能中途纠偏（发现方向错误/优先级变化/需求变更时能及时止损）。

格式：
```
[阶段X完成] <内容一句话>
- commit: <hash 或 WIP>
- 验证: <跑了什么、结果>
- 下一阶段: <做什么>
```

### 第 23 条：E2E 必须验渲染，不只验数据（2026-10-10）

**问题**：自动化全绿但画布不动——已发生 N 次：
- P1.1（TS 引擎渲染未接线）
- probes UI 出口（数据在但学生看不见）
- 装置 fallback Box（检查器说 0 缺失但全是方块）
- 天体动画（物理正确但画布网格不动）

**要求**：涉及"物体在画布上运动"的场景，E2E 必须包含画布动画断言：
- 运行中取 2 帧的 mesh.position（或 subjects/poses 位姿）
- 断言至少一个 subject 的 x 或 y 变化 > 阈值（默认 0.02 单位）
- Java 路径用 `B.subjects()`、TS 路径用 `B.tsPoses()`

**builder-check 集成**：每模板运行时自动采样并报告动画状态（三分类：
动画确认 / 有主体未动⚠️ / 无主体/装置）。扫描发现的批量缺口，必须列清单+批量修，
不许逐件挂账。
