**维护机制（新元件/新参数 checklist · 2026-09-30 追问5 全机械化）：**

| 条目 | 强制机制（跳过会被抓） |
|---|---|
| 1. catalog 加 `P()/SEL()` → 必须有消费点 | **CI v2 BLOCKING**（npm run verify + pre-commit，红=忘写） |
| 2. 消费走改名/表达式 → 本表"Java 路径元件"节加映射行 | **pre-commit co-change 钩子**：staged 含 catalog.ts 但不含本表 → 提交被拒 |
| 3. 新增合并 case → 本表 ③ 节登记+分流证明 | **CI v2 合并 case 白名单**（未登记的 `case 'x': case 'y':` → exit 1） |
| 4. v3 断链 → 修复或登记 | **CI v3 BLOCKING+ALLOWLIST**（白名单条目=放行签字，diff 可审） |

钩子可被 `--no-verify` 绕过——所以评审是第二道门：白名单条目、审计表 diff、合并 case 登记都在提交 diff 中可见，评审 AI 逐提交审计。
